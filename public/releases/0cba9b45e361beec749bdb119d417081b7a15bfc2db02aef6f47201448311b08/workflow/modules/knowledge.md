# 知识模块

仅约束 `knowledge.read/propose/update` 和对应 Wiki 产物。发布确认、CAS、后端 readiness 与文章规范不适用于普通代码、Markdown、方案留痕或其他模块；它们继续按各自 owner 和通用安全规则执行。

知识沉淀是可选扩展，不是普通代码任务的阻塞条件。接口语义固定为：

```text
knowledge.read → knowledge.propose → knowledge.update
```

- 用户明确维护知识库时启用；任务完成后形成稳定、可复用结论时每个任务只提示一次。已明确选择 `selfopenwiki`（包括当前 `knowledge` profile 的默认后端）且命中下述预览排障场景时，可选只读查询已有知识；不创建候选或发布事务。
- `read` 只读；`propose` 只生成候选，不发布；`update` 需要明确写入授权、来源/版本校验和可恢复发布。用户直接要求“总结到 Wiki”“更新此条目”或“审核后发布”即授权对应主题与目标；核对后执行，不再索要一次同范围的“确认写入”。仅要求草稿、方案或是否发布不明时不发布。
- 后端必须是显式 adapter，声明能力、失败语义和 Skill；不得猜测模型、数据库、OAuth 或路径，不把私人推理写入知识库。
- 知识正文和来源说明使用中文。凭据、token、临时事务、完整原始敏感材料和无效结论不写入正式知识。
- 后端缺失、能力不明或证据漂移时标记 `unverified`；普通代码交付可继续，并记录待同步事项。

## `knowledge` profile 默认路由

本模块定义生命周期、后端选择与知识文章质量规范。操作细则交给 `methods/kg-selfopenwiki/METHOD.md`，
该入口仅加载当前操作的一个引用；不要同时加载模块内部 Writer Skill 或完整 MCP 契约。
仅 profile 含知识能力不触发 Wiki；用户明确另选后端时服从其选择。

文档入口模式使用明确提供的个人偏好；没有个人文件时，用户明确要求个人 Wiki 且未另选后端，公共默认后端为 `selfopenwiki`。不要求 artifact/profile 才能读取本模块，不从磁盘猜个人配置。工具和 Wiki 根仍以该次实际 status 为准。

安装兼容入口当当前 SelfWorkflow artifact 的 profile 为 `knowledge`，且用户提到“打开/可视化 Wiki”、
“总结/整理 Wiki”或“更新/沉淀到 Wiki”时，默认 backend 固定为 `selfopenwiki`：

1. 本次 Wiki 操作首调 `openwiki_status`，不约束其他模块的工具顺序。
2. Wiki root 只接受 status 返回的 `paths.wikiRoot`；不读取 Agent 自己的 Wiki Markdown，
   不猜测其他 Wiki 目录。
3. 可视化使用 SelfOpenWiki status 中声明的新版 Viewer contract；旧 OpenWiki CLI 不
   是 fallback。
4. `knowledge.read` 使用 verified 的 `openwiki_read`：先取得目录/revision，再读取选中页面。
   缺能力时报告 `unverified`，不切换 `legacy_provider`。读取不启动发布事务。
5. 写入仍必须经过 SelfWiki personal lifecycle、有效用户授权、Review 和 CAS 发布。必要的来源页、主题导航和链接同步可纳入同一主题计划；跨主题重组、删除知识、来源权限变化或未授权 Git 操作另核对授权。

能力按操作判断：发布未就绪不自动禁止安全读取或 Viewer；读路径检查 `knowledge.read.safe` 及后端一致性结果，Viewer 检查 live contract，更新才要求发布生命周期。`restore_required` 仍禁止不一致的读取/写入；Viewer 的直接文件浏览不承诺快照一致性。

经 WheelMaker/Relay、反向代理或 iframe 的开发预览持续加载、空白或静态脚本 403 时，
可按 `kg-selfopenwiki` 的 `references/preview-troubleshooting.md` 只读查询已有排障知识。
普通网页慢、模型失败或任意 API 403 不命中；另选知识后端时遵循该选择。知识工具、
readiness 或条目不可用时记录该知识证据缺口并继续原诊断，不能成为 UI/代码修复的前置门禁。

## 知识文章质量规范

在知识候选规划、写作和 Review 时应用；只读查询、打开 Wiki 不额外加载写作材料。
默认读者熟悉主题背景，但无需打开源码或原始材料也能理解正文。UE 专题默认面向熟悉 UE
概念的读者，其他领域按各自背景调整。以下要求按文章类型和主题适用，不为满足清单
虚构算法、接口、设计理由、性能收益或图像。

### 完整方向、紧凑叙述

- 一个页面完整回答一个稳定问题或技术方向：先解释要解决什么、为什么这样设计，再展开
  核心机制、数据交接、取舍与边界；用目录和稳定锚点支持跳读。
- 将依赖相同上下文、内容过少的短页合并为有逻辑的章节；不按文件、符号、原稿小节或
  来源数量机械拆页。紧凑意味着减少重复背景与往返跳转，不能删掉关键算法和因果解释，
  也不能将旧短页直接拼成无主线长页。不设固定页数、字数或配图数量。
- 独立主题保持并列导航；拆分应有独立问题和阅读价值。合并、迁移时同步目录、内部链接、
  锚点和旧入口处置，不遗留重复 canonical 页面或断链。

### 概念、接口与源码讲解

- 先建立概念模型，再给出符号。首次引入关键接口或类时说明中文职责、主要输入输出，
  以及它在整条调用链或数据链中的作用；不能用一串函数名、类名代替解释。
- 按需要串起入口、owner、producer、变换、consumer、持久化产物和失效/释放条件。
  关键结论讲清原因、不变量、失败路径与适用限制；不能只列“当前代码对应哪些文件”。
- 当文字不足以解释关键机制时，提供短小且可追溯的核心实现、数据结构或明确标为简化的
  伪代码，并逐段解释其作用。注明适用版本和源码位置，保留必要语义，不贴整份源码凑深度。

### Agent 实现与复现契约

技术实现类主题默认同时面向需要移植、重建或修改功能的 Agent；在上述可读性要求上，
正文应详细到足以据此搭建一个边界明确、可检查的功能闭环。只讲概念、列符号/文件或让
Agent 回源码自行补齐关键算法，不算完成实现说明。该要求用于新增或实质更新的技术主题；
导航、来源页、会话摘要、非技术文章和纯链接/措辞修正只承担各自职责，不因此重写整库。

规划时在现有 canonical 主题内标出下列适用项的章节/锚点、来源与缺口；跨篇专题可按
数据依赖组织一份实施指南，链接各篇实现契约，避免另复制一套算法正文。不强制固定标题、
独立页面或空表格；不适用项说明原因，适用但缺证据的项明确标为缺口，不能填作“不适用”。

| 实现问题 | 正文必须给出的信息（按主题适用） |
| --- | --- |
| 为什么这样设计 | 目标、约束、概念模型、设计取舍与关键不变量；区分源码事实、明确设计依据与作者推断，不把推断写成原作者意图。 |
| 数据怎样表达和流转 | 关键结构/字段的类型、含义、单位/坐标/精度、容量和无效值；owner、初始化、producer/consumer、持久化、更新、失效和释放；按需说明线程/队列及同步边界。 |
| 接口怎样接起来 | 入口、调用顺序与时机、函数职责、主要输入输出、前后置条件、副作用和返回/提前退出语义；输出何时有效、失败时消费者如何处理。 |
| 算法怎样实现 | 按数据依赖展开核心步骤、分支顺序、公式及边界处理；用带版本/出处的短实现或明确简化的伪代码覆盖关键变换，不能省掉决定正确性的语义。 |
| 哪些环境和分支成立 | 适用源码版本与工作区差异、依赖/资产、Platform、RHI/Feature Level、Shading Path、材质/视图类型及编译/运行开关（如 CVar）；区分编译支持、运行准入和实际生效值，写清条件组合、优先级/提前分支和不满足时的回退/禁用行为。 |
| 怎样紧凑存储或计算 | 对实际存在的位打包、索引映射、压缩、池化、缓存与工作列表裁剪，说明布局/位宽/范围、编码解码、对齐/精度/容量、不变量及生产消费两端；给出必要边界例子，收益与代价区分设计预期和实测。 |
| 按什么顺序搭建 | 最小依赖和可复用前提、逐步实施顺序、每步产物及可观察的验收出口，再逐步加入优化/可选分支；“建议移植顺序”与源码实际调度顺序分别说明。 |
| 改动影响哪里 | 关键路径/符号与上下游影响关系，按需覆盖资产/构建产物、序列化/ABI、CPU/GPU 布局、Shader permutation、缓存/history 和最终消费者；说明必须联动修改的两端及兼容/失效风险。 |

复现步骤应绑定一个明确目标，例如“重建最小功能闭环”“复现已知故障”或“比较两个开关的
结果”。给出环境与依赖、最小场景/输入、配置的有效值或取得方式、按序操作、观察位置、
预期结果/允许误差、失败信号及必要的清理/恢复。命令、路径、配置值和测试向量必须有
来源；待填项标清取得方法，不能伪造可以直接运行的命令。按适用性覆盖正常、失败、边界、
开关禁用/回退、容量与跨帧/状态失效用例，不把一张正常截图当全部验收。

关键实现结论就近绑定源码路径/符号和版本；跨文件布局与编码须核对生产、消费两端，
不能仅凭声明推断完整算法。源码未覆盖的核心行为写明缺口与对复刻的影响，沿用后端的
minor/provisional/blocking 分级，不扩大来源权限。保留足够精确的常量、公式、输入输出
例子与不变量；文末维护身份后移不能移走决定实现正确性的细节。

提供复现方案不等于复现通过。分别记录源码核对、静态检查、编译/测试、设备/GPU 运行及
实际复刻结果；未执行项写明原因和下一步，不能将计划、推断或静态一致性称为运行验证。
写作规范不额外授权编译、清缓存、运行高成本实验或修改业务代码；遵循当前任务的授权、
禁编译及缓存保护约束，不以“提升可复现能力”为由改变共享环境。

### 图像用于建立直觉

- 技术机制配图默认优先使用 Agent 直接编写、可编辑并可版本管理的 SVG 概念示意图，
  精确控制几何形状、中文标签、配色和布局；保留可维护图源，不只交付栅格截图。
  沿用已有清晰图形的视觉语言，但不要求无收益地重绘现有合格图，也不绑定专用绘图 Skill。
- 空间、视锥、覆盖、缓存布局、分层和生命周期等内容优先考虑直观示意：俯视/截面、区域
  叠加、分层布局、前后对照、时间轴或设计图；真实顺序与依赖才适合流程图。图像选型服务于
  理解，不为装饰配图，也不把所有关系强行画成流程图。
- 用空间布局、包围区域、分组与小规模具体例子解释机制，例如“一个组跨多个存储页、一个页
  容纳多个组的部分”。关系、映射与容纳关系不能仅用串行方框和箭头代替；例子必须说明
  对应概念及抽象边界，不能暗示虚构的分配算法、真实容量或运行结果。
- 简单的真实流程、依赖图可继续使用 Mermaid；照片、艺术性插图等确需位图时才使用
  imagegen，数据图表按相应绘图方法处理。不能以自动流程排版或生成式位图替代需要精确
  标签与布局的技术概念图，也不因优先 SVG 而把其他合适图形一律改写。
- SVG 保持文字可读、缩放不失真，提供 `viewBox`、`title`/`desc` 或等效可访问说明；
  不包含脚本、事件属性、`foreignObject` 或外部资源依赖。独立图源与正文内联副本同时
  存在时须保持一致；在正文实际阅读宽度检查标签、图例、边界与留白。
- 图前说明要回答的问题，图后解释读图结论；提供图例/文字说明，标明示意、非比例、坐标、
  单位与抽象边界（按需）。符号、色彩和箭头含义应一致，不能只依赖颜色传达信息。
- 图文与来源结论相互核对，不能把抽象图当真实算法、精确比例或已验证运行结果。检查
  标签可读性、裁切、重叠、资源引用和版面；能渲染时实际检查，未渲染明确记录，不能以
  SVG/XML 解析通过代替视觉检查。图内文字、图注和替代文本同样适用可读规范。

### 正文与维护信息分层

- 正文使用中文可读结论，例如“本次源码已确认”“旧版实现”“仍需设备验证”，并说明对
  理解和使用的影响；不以 `confirmed/source-backed/watchlist/contested` 等机器标签堆叠开篇。
- SHA/hash、完整 commit/blob、manifest/source UUID、构建 GUID、raw 来源编号及审计流水
  放到文末“来源与维护注记”，支持折叠时使用折叠块；来源/索引页同样先解释来源角色和版本
  范围，精确指纹置于末尾。正文保留有意义的源码定位链接，使用可读标题，不拿指纹当标题。
- 精确身份和证据关系仍保留在结构化字段及维护区；不要改写工具协议、Claim、回执或
  内容哈希，也不要为了清除指纹而破坏必要源码片段/测试向量中的精确常量。
- 影响正确性的版本差异、冲突、风险与未执行验证必须在相关正文就近说明；不能随维护
  标识一起折叠隐藏。对暂时无法对齐的版本，保留适用边界，不推断已实现或验证通过。

### 候选与发布验收

复用当前任务的独立 Review 和发布授权，不另起确认循环。按内容核对源码/材料一致性、
整体架构和跨篇逻辑、术语解释、知识方向完整性、图文准确性，以及正文/图注/来源页中的
维护标识后移。技术实现类主题还须按上述覆盖关系检查实现细节，并选一条代表性闭环做
文本走查：Reviewer 仅依据候选正文及其显式链接的契约，能否确定输入、环境分支、数据
布局、实施顺序、中间产物和验收结果；再用获授权的来源核对正确性。依赖未写出的关键
步骤、缺失的配套编码/消费端或无法判定成功的复现步骤，都是需修正的内容缺口。
文本走查不要求 Reviewer 执行代码，也不等同于实际复刻成功。再检查链接、锚点、图形和呈现。
静态源码阅读、结构检查、视觉检查和实际
运行验证分别记录。发现问题先修候选并复核受影响部分；只有适用 Review 与后端发布
门禁通过后才报告正式更新成功。
