# 代码变更建议与边界

供实际变更或需要验证的诊断按问题参考；不要求首次编辑前另建实施契约、填固定字段表或完整执行某条状态链。用户/项目明确要求的过程、审查和操作限制仍须遵守。

## 判断与取舍

结合预期/实际、真实输入和观察点定位问题；必要时追踪状态生产、转换、消费及失效边界。对持久化或恢复的要求，用对应落盘、重开或恢复结果验证，不能用退出码、dirty 或同进程状态冒充。

优先处理真正违反约定的责任层。来源证据不足不等于上游违约；下游可按自身契约拒绝、延后或改进诊断。先利用能满足验收的原生能力；不因缺证据自动增加长期证明、审计或信任体系。

方案说明深度取决于实质选择与影响。已有明确的目标、范围、风险或验证安排直接复用；简单修改无需凑替代方案或过程文档。出现公共 API/ABI/Schema、持久格式、公共头/枚举/注册矩阵、全局构建选项、共享热路径或跨模块基础设施变化时，应结合实际影响评估兼容性、验证、维护与回退代价；这些是风险线索，不是按关键词重启审批的清单。

## 授权与保护

任务请求覆盖既有边界内的必要工作，必要支持继续；相邻问题、可逆性、沉没成本或验证失败本身不扩权。实质改变目标、约定保证、允许范围或引入未覆盖的重要影响时，给出具体差异后确认；已明确覆盖该影响及风险的授权沿用，只暂停相关动作。

检查和隔离任务增量，保留无关既有修改与并发工作；无法安全区分重叠时暂停受影响编辑。涉及部分写入、持久状态、缓存、恢复或临时产物时，按其实际生命周期考虑失败保护和恢复，不为不涉及的状态建账。

保持无须变化的稳定调用者，不为命名一致、一次复用、假想未来或测试方便扩展迁移。真正共享的不变量和必要验收可支持有界调整，仍须处于授权范围。

测试选择服务于目标和证据，不反向扩张生产架构。优先既有接口、扩展点、窄接缝或黑盒；不能为了测试方便擅自增加公共枚举、改变注册矩阵/对象布局或铺设共享路径分支。缺证据如实说明，继续寻找范围内的有效核验。
