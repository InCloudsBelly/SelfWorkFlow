# Wiki 设计边界逆向质询

用于技术 Wiki 新增、实质更新和明确质量评估；统一指标与状态见[主标准](wiki-quality.md)。沿用已有范围基准、题单、PageJob、Reviewer 与发布流程，不启动用户访谈或额外 Reviewer。Agent 自行查获授权事实，只有真实用户决策缺失时才提问。

## 四步完成质询

1. **文档提问**：仅据绑定候选和显式同版契约，逐实现单元列目的、选择、前提、依赖及未知；按决策依赖先问前置问题。每题记文档位置、可观察预期或文档无法判定、能区分答案的边界/反例，绑定题单后再核代码。
2. **代码裁定**：绑定版本/路径/符号，工作区差异影响结论时绑定有效内容。追到入口、判断、生产/消费、状态更新及退出/回退，核对正常、失败、边界和必要条件组合。题目结论为代码支持、代码反驳、仅在所列条件下支持或未核实；范围不完整不作不存在的断言。
3. **补题与修文**：源码发现新前提、分支、耦合或单元时标为核验后新增问题，补入范围基准；保留初始清单，不倒填发现顺序。反例推翻旧答案则回查前置问题，直到关键前提有可定位答案或明确缺口。同步修正文、公式、图注和跨页契约，不能只加 FAQ 留下矛盾正文。
4. **独立回查**：Reviewer 先凭最终候选自选问题/反例，再核来源和作者问答；覆盖全部关键实现单元，检查隐含前提、被否定假设及跨单元耦合，不只复述预设答案。修订仅复核影响项和未解问题。

范围按任务、来源和实际机制确定，不按每函数/每行代码凑题，也不只选最易正常路径。共享问答直达同版规范章节，使用处给本节结论及额外条件；按 L1 区分必要契约、选读与证据。
作者或 Reviewer 已看过源码须披露，仍逐项要求正文证据，不声称盲测。不存在初稿时先形成候选再查可回答性；原由源码整理的内容不假装此前未接触来源。

## 每个单元追问什么

按实际机制选题，不要求填满无关问卷。

| 方向 | 问题与核验要点 |
| --- | --- |
| 目的与选择 | 解决什么问题、受什么约束、为何选此表示/顺序/算法；替代方案何时不同，取舍是有记录还是推断。 |
| 前提与不变量 | 输入、范围、单位、对齐、容量、状态何时有效；谁建立/检查/消费，由类型、判断、调用者还是约定保证；违反后报错、截断、回退、未定义还是未知。 |
| 条件组合 | 编译支持、运行准入、有效配置、优先级与提前分支如何组合；返回后产物是否有效、消费者如何识别。 |
| 所有权与时间 | 谁创建、更新、同步、失效、释放；空输入、重复调用、部分失败、并发/跨帧旧状态及配对时序约束在哪里落实。 |
| 反事实与扩展 | 改容量、位宽、精度、坐标、同步、步骤顺序或平台会破坏什么；区分可配限制、兼容约定、算法前提和实现限制。 |
| 修改与验收 | 哪些生产/消费、持久化、缓存/历史状态或资产须联动；最小正常/边界/失败例的预期、失败信号和恢复是什么。 |

反事实不授权修改代码或运行实验；无依据不声称作者曾放弃某方案。为每题给具体因果和条件，泛化的性能/维护理由或题目数量不算充分解释。超出主题的延伸问题单列待研究，不无限追问。

## 答案的依据类别

| 类别 | 必须分清的边界 |
| --- | --- |
| 实现事实 | 当前源码确实做什么、在什么条件和版本成立；存在路径不等于目标环境运行过或性能实测成立。 |
| 已记录意图 | 设计说明、ADR、注释、提交说明明确表达的目的/取舍及版本；须与当前实现核对，冲突就近说明。 |
| 解释性推断 | 写明假设、简明理由和可反驳条件；不能把代码如此写当作作者必然如此想。 |
| 未知/冲突 | 缺什么、影响哪些结论和实施、何处补证；缺陷与期望契约分开，不替缺陷补造意图。 |

原始动机未知不自动扣分：行为、边界、影响已核实且推断标清时可达标；关键行为或边界未知仍是缺口。常量只证明当前取值，不能单凭它证明硬件上限、算法极限或兼容承诺。静态、测试与运行证据分别记录。

## 固化到正文的问答

最终问答放在相关实现章节，可合并表格或分段配图；标题是具体问题，ID/锚点稳定，语义至少包括：

```markdown
### DQ-<稳定ID>：<具体问题>
问题与范围：<单元、条件、版本、待裁定命题>
回答：<直接结论、原因、不变量、条件变化后的结果>
核验结论：<代码支持 / 代码反驳 / 仅在所列条件下支持 / 未核实>
依据类别：<分别标明事实、已记录意图、推断或未知>
依据与边界：<正文契约及源码位置、两端/分支核对、证据限制>
例子与反例：<输入/状态/配置 → 结果或失败信号>
修改与验收：<联动部分、允许扩展、检查出口，按适用性给出>
未解事项：<待补证据和影响，或无当前已知关键缺口>
```

正文保留有意义的版本和定位，精确 hash/流水放维护区；冲突、限制和未验证结论仍就近说明。题单初版、文档预测、来源范围、单元→题目→正文对应、既有源码暴露和评分留在已有任务记录；仅保存面向读者的论证，不保存 Agent 私有推理、草稿链或问答流水。审查报告或源码链接不能代替正文答案。

示例：初稿写四位索引容纳 16 个对象，应先问是否所有码值都有效。若生产端拒绝 `>=0xF`，消费端把 `0xF` 判空，则应区分 16 种编码与最多 15 个有效索引；实际容量还须查分配约束，并用 `0xE`、`0xF` 和越界值说明结果。代码不单独证明作者为 ABI 兼容而如此设计。此例是假设方法演示，不是项目核验结果。

写 Wiki 实施说明时应用本方法；只评估不自动发布，维护规则不自动改既有 Wiki；普通代码解释或显式架构访谈各走原任务，不因术语触发本方法。
