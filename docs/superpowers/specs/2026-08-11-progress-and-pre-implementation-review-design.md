# SelfWorkFlow 进度反馈、代码实施契约与实施前整体 Review 设计

- 日期：2026-08-11
- 状态：既有进度/整体 Review/侵入性预算已作为受保护基线；当前仅设计尚未实施的“代码实施契约”增量，等待独立整体 Review 与最终用户确认
- 适用范围：轻量 Agent Policy、Full/Deep 文档包、V2/V3 planned 阶段
- 取代范围：取代 `2026-08-08-modular-workflow-orchestration-design.md` 中“普通 Plan 不单独启动独立 Review”对 Full/Deep 和正式文档包任务的描述；Light 内联任务维持原行为

## 1. 问题与目标

当前生命周期能够记录阶段状态，但安装后的 Agent 不会稳定告诉用户“现在执行到哪里、还剩哪些阶段、还要多久”。复杂任务还可能分别审查设计、TEA 测试设计和实施计划，却没有在动工前让一个全新上下文同时检查三者，因而遗漏跨文档矛盾、测试缺口和不可实施步骤。

本文件最初同时规划进度反馈、整体 Review 和侵入性预算；这些能力已经在当前 HEAD `08640be26b051354615941a11a65342a9a953297` 及进入本任务前的工作树中形成。当前任务不追溯宣称它们满足新门禁，也不回滚或重做它们；它们作为用户已有、受保护的基线。本轮第一次代码编辑前门禁只约束尚未实施的“代码实施契约”增量。

本次只解决四件事：

1. 用低噪声的进度更新展示当前阶段、粗略完成区间、剩余阶段和预计剩余时间；
2. 对 Full/Deep 或正式文档包任务，在实施前强制启动独立 SubAgent，对最终设计、测试设计和实施计划做整体一致性 Review；
3. 把“严格控制代码设计侵入性”设为设计、计划和最终 diff 的硬性不变量，防止局部功能或测试需求穿透公共契约和通用生产路径。
4. 对所有会修改代码的任务，在第一次编辑测试或生产代码前形成并由用户明确确认一份“代码实施契约”，使修改预期、侵入性、安全、性能和可维护性先完成讨论与收敛。

不新增任务数据库、后台计时器、精确百分比算法或新的长期运行服务，也不以实施前 Review 取代实施后的完整 diff Review。

## 2. 方案比较与选择

### 2.1 进度反馈

- 方案 A：按每个工具调用播报。反馈及时，但噪声和上下文成本过高。
- 方案 B：只在最终交付时汇报。成本最低，但无法解决等待感知问题。
- 方案 C：事件驱动的阶段播报。开始、主阶段切换、长阶段检查点、阻塞或估算变化时更新。

选择方案 C。它复用现有生命周期，不创建新的持久状态。

### 2.2 实施前 Review

- 方案 A：继续只做设计、计划或分块 Review。无法发现跨文档不一致。
- 方案 B：新增独立生命周期阶段和专用 Review 服务。机械约束强，但会扩大 Schema、Host 和迁移范围。
- 方案 C：强化既有 planned/`plan.gate`，在其通过前增加独立文档包 Review。

选择方案 C。V2 复用 `plan.gate`；V3 在 `planned` 阶段增加一个有条件的 `plan.integrated-review` 插槽。该能力仍如实标记为 Agent Policy/运行时能力：具体 Agent 必须真正提供独立 SubAgent，不能用同一上下文自报代替。V3 模块的运行时能力保持 `unverified`；没有通过 `explicitModuleIds` 或 `projectDefaultModuleIds` 请求，并同时由 execution policy 授权时，Full/Deep PlanGraph 必须 fail closed，而不是假定宿主支持。直接读取用户指令的普通 Agent 仍按嵌入策略执行，并在没有 SubAgent 时暂停实施。

### 2.3 代码实施契约

- 方案 A：复用现有 Brainstorming、TEA、Writing Plans 和 `plan.gate`，为所有代码修改增加统一的实施前契约。Light 在对话内使用紧凑摘要；Full/Deep 将契约分布写入设计、测试设计和实施计划，并在独立整体 Review 后汇总给用户确认。
- 方案 B：只要求 Full/Deep 正式文档记录契约。上下文成本较低，但小型 Bug 修复仍可能以“改动很少”为由越过高影响半径边界。
- 方案 C：新增独立生命周期阶段、Schema 和专用模块。机械约束更强，但会扩大路由、迁移和运行时成本。

选择方案 A。代码实施契约是既有门禁中的必填内容，不新增模块、持久状态或默认 Skill。用户一次确认批准的是最终边界；批准范围内的局部实现细节不重复询问，越界才使确认失效。

## 3. 进度反馈契约

### 3.1 触发时机

需要工具、文件修改或外部副作用的任务，在首条进度更新中报告工作流 profile、模式和初始估算。之后仅在以下事件更新：

- 进入新的主阶段；
- 一个阶段持续较久，且宿主需要保活或已经出现可验证的新检查点；
- 范围、阻塞或证据使剩余时间明显变化；
- 进入等待用户、暂停或失败状态。

不得按每个命令机械刷屏。只读短问答和预计立即完成的机械操作不强制额外进度条；宿主自身更严格的保活规则继续生效。

### 3.2 最小显示字段

进度更新使用一到两行，至少包含：

```text
SelfWorkflow active: <profile>；mode: <Light|Full|Deep>
进度 <已完成主阶段>/<总主阶段>（约 <区间>%）｜当前：<阶段/目标>｜剩余：<关键阶段>｜预计：<时间区间或何时重估>
```

- 百分比只能是粗略区间，不得使用 `50%` 这类单点精确值伪装为测量；正常进展保持单调，范围变化造成明显回退时必须说明重估原因；
- 时间必须使用区间，例如“20–40 分钟”，不能承诺精确完成时刻；
- 信息不足时写“暂无法可靠估算，将在完成 `<检查点>` 后重估”，不得虚构 ETA；
- 估算失效时主动重估并简述原因；
- 最终回复以真实 Review、测试和残余风险为准，不能用“100%”代替完成证据。

建议阶段带仅用于沟通，不参与完成 Gate：范围/上下文 0–15%，设计 15–30%，测试设计与计划 30–45%，实施前整体 Review 45–50%，实现 50–75%，落地 Review 75–85%，验证 85–95%，交付与可选知识提示 95–100%。Agent 可按任务调整区间，但必须保持单调且说明明显重估。

## 4. 实施前整体 Review 门禁

### 4.1 适用边界

以下任一条件满足时，实施前必须执行：

- 任务强度为 Full 或 Deep；
- 任务已经形成设计、测试设计、实施计划中的至少两份正式文档。

第二种情况必须在实施前把任务升级到 Full，不允许继续伪装成 Light。普通 Light 内联设计/计划不启动 SubAgent，也不要求为了触发门禁而额外制造文档。TEA 不适用时可以没有独立 TEA 文件，但文档包必须记录不适用原因和最窄充分测试策略。

### 4.2 独立性和输入

门禁必须启动新的独立 SubAgent/上下文，且不得继承主 Agent 的私有推理过程。只提供：

- 已确认的目标、范围、验收条件和项目硬规则；
- 最终设计、TEA/测试设计、实施计划的完整内容、路径和内容 hash；
- 必要的代码或接口事实来源；
- 要求输出的结构化 Review 契约。

分块 Review、同一 Agent 自审和旧版本文档的 Review 都不能代替本门禁。SubAgent 必须只读，不得修改仓库或开始实现。

### 4.3 Review 范围

整体 Review 至少检查：

- 每项需求和验收条件是否同时落入设计、测试与实施步骤；
- 三份文档的术语、接口、状态、不变量、失败路径和顺序是否一致；
- TEA 风险优先级、测试层级和实施步骤是否能真实验证目标；
- 安全、敏感数据、兼容性、持久数据、侵入性、回滚和用户已有修改；
- 计划是否可执行，文件路径、依赖、TDD Red/Green 和验证命令是否闭环；
- 是否存在靠下游补偿掩盖上游责任层错误的设计。

### 4.4 代码实施契约

任何会新增、修改或删除行为代码的任务，在第一次编辑代码前都必须形成代码实施契约。这里的代码包括生产代码、测试代码、Shader、构建脚本和会改变运行行为的配置；纯文档任务不适用。确认前允许只读代码检查、非破坏性诊断以及编写和修订设计/测试/计划文档，但不得先写测试代码或生产代码。

Light 任务使用对话内的紧凑契约，不要求额外文档或独立 SubAgent。Full/Deep 或已经形成正式文档包的任务必须分别写清：

- **设计/规格**：目标行为、根因责任层、候选实现、选定方案和取舍；预期影响的模块、主要文件/符号、数据流与公共契约；安全、性能、兼容性、长期维护和回滚预期。
- **TEA/测试设计**：直接路径、失败路径、状态不变量和回归面；测试接缝位于哪里；如何避免测试覆盖反向塑造生产架构；性能或资源回归如何观测，无法自动取得的证据如何标记 `unverified`。
- **实施计划**：按步骤列出预计修改的责任层、文件和行为，引用已批准的侵入性预算；写明禁止触碰的边界、TDD Red/Green 顺序、回滚和验证命令。

Full/Deep 的最终文档包必须先通过新的独立 SubAgent 整体 Review；主 Agent 修正所有 Critical/Important，并处置 Minor 后，再把最终代码实施契约摘要提交给用户。摘要至少包含：预期代码改动、影响半径/侵入性、安全、性能、可维护性/回滚、主要替代方案及未验证项。只有用户对这份最终摘要作出明确实施确认后，才能开始 TDD 或任何代码编辑。一般性的需求认可、旧版本设计确认或 SubAgent 推荐不等同于该确认。

以下任一变化会使确认和相关 Review 失效：改变根因责任层或跨出已批准模块；新增公共 API/枚举、ABI/Schema/持久格式、全局宏或 Build 变体；扩大共享热路径或测试来源的生产改动；实质增加安全风险、性能成本、长期维护或回滚成本；改变关键测试接缝。Agent 必须停止编辑，修订受影响文档和契约，重新 Review，并再次取得用户确认。只要仍处于批准的责任层、影响半径和风险预算内，文件内局部细节、命名和等价实现调整无需反复询问，但必须在 post-landing Review 中报告。

### 4.5 侵入性预算

最小侵入不是“尽量做到”的偏好，而是验收不变量。侵入性按影响半径判断，不按修改行数判断：几行公共宏、公共枚举、ABI、Schema 或 Build 配置改动，可能比数百行局部实现具有更高维护成本和兼容风险。

设计和计划必须选择能够满足目标的最窄责任层。出现以下任一信号时，必须显式记录侵入性预算，并至少比较一个更窄替代方案：

- 修改公共头文件、公共 API/枚举、ABI、序列化或持久化格式；
- 新增或扩散全局编译宏、Build Flag、Target/Platform 配置或条件编译矩阵；
- 为局部功能改动稳定底层基础设施、跨模块公共注册表或共享热路径；
- 为测试增加生产符号、生产状态、测试专用公共槽位，或把测试分支穿透通用生产代码；
- 实际修改跨出已批准的文件、模块、责任层或编译变体。

侵入性预算至少包含受影响文件和层级、公共契约与编译变体、长期维护/兼容成本、回滚方式，以及为何更窄方案不足。存在满足验收的更窄方案时，禁止选择更重方案。确实没有更窄方案时，跨越上述边界属于关键决策，必须先获得用户明确确认；不得由 SubAgent、TEA 或实施者自行批准。

测试覆盖不能反向驱动生产架构膨胀。优先使用测试自有 TU/模块、既有扩展点、窄接口注入、捕获工具和黑盒验证。`WITH_DEV_AUTOMATION_TESTS` 等宏可以保护测试自有代码或既有局部测试接缝，但默认不得用来改变公共枚举/布局、枚举 `Num`、公共注册表容量或注册矩阵、ABI，或在通用生产路径中传播测试专用分支。如果最低测试证据必须依赖未经批准的高侵入改造，应如实标记该项 `unverified` 并提供人工验证方法，而不是修改生产架构来让测试更容易。

实施前整体 Review 必须检查计划中的侵入性预算；post-landing Review 必须比较预算与最终 `intrusion delta`，至少列出公共头文件、Build/宏、公共契约、跨层依赖、测试来源的生产改动和编译变体。实际 diff 超出预算时，旧设计与 Review 失效，必须停止实施并回到设计/用户决策，不能静默扩张。

### 4.6 闭环和失效规则

Review 输出 `pass` 或 `changes-required`，并将发现分为 Critical、Important、Minor：

- Critical、Important 未解决时禁止实施；
- 每个 Minor 也必须有明确处置：修复，或在不影响验收、安全、兼容性和侵入性的前提下记录接受/延期及理由；
- 发现需要改变范围、验收、公共接口、安全或持久数据时，回到用户处理关键决策；
- 发现存在更窄可行方案、测试需求正在塑造公共生产架构，或实际侵入面超过预算时，禁止通过；
- 任一受审文档变化都会使旧整体 Review 失效；必须对新的完整文档包重新启动独立 Review；
- 只有当前文档包 hash 对应的 Review 通过，`plan.gate`/`plan.integrated-review` 才能通过并进入实现。

如果 Agent 不具备真正独立 SubAgent 能力，必须把门禁标为 `unverified` 并暂停实施；本门禁不允许同一 Agent 结构化自审降级。用户可以改为只交付文档，但不能把未通过门禁的任务称为可实施。

## 5. 与现有流程的关系

```text
Brainstorming / 可选 Grill-me
-> design.gate
-> TEA 测试设计 + Writing Plans
-> 分块 Review（仍可保留）
-> 独立 SubAgent 整体 Review（新增硬门禁）
-> 用户确认最终代码实施契约
-> Implement / Debug
-> post-landing Review
-> Verify
-> Deliver / optional Knowledge
```

实施前 Review 检查“方案能否闭环实施”，实施后 Review 检查“最终 diff 是否正确落地”，两者不可互相替代。

- **历史受保护基线**：已有进度反馈、整体 Review、侵入性预算、V2/V3 `plan.integrated-review` 路由、Pipeline/Catalog 和 C7OpenWiki 改动均不在本轮修改范围；本轮只做回归验证。

- `workflow/core.md` 和 `skills/code-quality/SKILL.md` 各使用一个只包含该路径的本地 source-lock 技术提交；不 push、不夹带其他脏修改。对应 Catalog 只更新 revision/contentHash，不改变 source-lock 契约。
- 测试只证明规则、既有路由和安装产物存在且边界正确，不虚构 Agent 在真实会话中的语义遵循；真实独立 Review 与压力验证作为 Agent Policy 证据。

| 回滚 | 发布失败由安装事务自动回滚；发布成功后可使用该事务生成 rollback plan 并以其 hash 回滚到当前 artifact `sha256:81892d78441f6bf6a9539caeaed616e4bb65a356555020780fa4b149e8ff7496`。Git 侧只创建两个限路径的本地 source-lock 技术提交，不 push；其他脏修改保持不变。 |

本次最终文档包明确由设计、TEA、实施计划和 dirty-baseline 审计清单四个文件组成，Review 与用户确认必须同时绑定四个 SHA-256。本次正式实施顺序固定为：完整四文件包独立 Review 通过并完成修正 → 向用户呈现本表和四个最终 hash → 用户明确确认实施 → 编写失败测试 → 最小策略/Skill/source-lock 修改 → Green、安装、post-landing Review。任一包内文件变化都使旧 Review 失效；任一契约边界变化都使用户确认失效。

## 7. 验收条件

1. 安装后的用户级指令能看到低噪声进度格式、ETA 不确定性规则和重估规则；
2. Light 内联任务不被强制启动 SubAgent；
3. Full/Deep 或至少两份正式文档的任务在实施前必须通过独立整体 Review；
4. Review 输入绑定最终文档包，文档变化后旧结论失效；
5. SubAgent 不可用时暂停实施，不静默同上下文降级；
6. 实施前 Review 不替代 TDD、post-landing Review 或 Verify；
7. 现有 C7OpenWiki 和其他未提交修改不被覆盖；
8. 运行最窄相关单元、行为、Catalog、运行时和安装器测试，并验证重新安装后的 `AGENTS.md`。
9. V3 PlanGraph 测试证明 Light 不适用、Full/Deep 未授权时暂停、显式授权后选择整体 Review 模块。
10. 代码设计按影响半径控制侵入性；公共契约、全局宏/Build 变体、跨层基础设施和测试来源的生产改动必须进入侵入性预算。
11. 存在更窄方案时禁止重方案；无更窄方案且需要越过高侵入边界时，必须作为关键决策获得用户明确确认。
12. 测试覆盖不得反向驱动生产架构膨胀；无法在批准边界内取得的证据必须标为 `unverified`，不得以公共测试槽位或通用生产分支换取可测性。
13. 所有代码修改在第一次编辑测试或生产代码前都必须形成代码实施契约并取得用户明确实施确认；Light 使用对话内摘要，不强制生成正式文档或启动 SubAgent。
14. Full/Deep 的设计、TEA 和实施计划分别覆盖修改预期、测试接缝/性能证据和具体落地边界；独立整体 Review 通过并修正后，用户确认最终摘要才允许实施。
15. 实际修改越过责任层、公共契约、侵入性、安全、性能或维护预算时，旧确认失效并停止实施；批准预算内的局部细节调整不重复询问。
