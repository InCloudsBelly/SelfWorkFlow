# SelfWorkFlow 轻量代码优先核心设计

## 背景与决策

现有首版把日常任务流程与工作流自身的安装、发布、原生验收和知识扩展治理放在同一默认入口中。后者仍有独立价值，但不应成为每次任务的上下文和执行成本。

本次采用“轻核心、显式扩展”的方案：仓库可以保留完整维护能力，默认运行时和默认路由只暴露代码任务所需的最小流程。删除重型能力会损失已完成工作；只缩短入口而仍打包全部内容则不能真正降低上下文与认知成本。

## 默认任务流程

默认流程只有六步：

1. 简短判断任务规模和风险；边界不清时升级一级。
2. 读取目标代码、项目规则和必要上下文，定位真正责任层。
3. 只有存在设计选择或跨模块影响时才执行 Brainstorming 和 Plan。
4. 在责任层做最小侵入实现，保护用户已有修改。
5. 审查完整 diff、逻辑闭环、失败路径、安全性和无关修改。
6. 执行与风险相称的最窄充分验证，并如实报告未验证项。

只读问答不进入修改流程。Grill-me 只由用户显式触发。知识沉淀在任务验证后按需提出，并且只有用户确认后才写入。

## 按需加载

默认入口只加载一份精简核心说明。代码任务按阶段最多追加当前真正需要的能力正文，例如设计阶段的 Brainstorming、实现阶段的 TDD 或调试、完成阶段的验证规则；不预加载整套 Superpowers、证据 Schema 或全部 Skill。

安全硬规则由精简核心摘要和确定性程序共同保证。详细证据格式、事务协议和发布治理只在维护 SelfWorkFlow 本身或执行对应操作时读取。

## 运行时分层

- `core`：默认。包含精简入口、代码质量核心、Catalog/路由结果以及目标 Agent 的薄适配器。
- `knowledge`：显式启用。在 `core` 上增加知识后端契约和 C7OpenWiki 适配器。
- `maintainer`：显式启用。包含安装、迁移、来源吸收、完整验证与发布治理。

安装、发布、原生 Agent 验收和 OpenWiki 不得因普通代码任务被隐式触发。仓库内部文件数量不等于 Agent 的默认上下文数量。

## 错误与降级

普通任务缺少可选扩展时继续交付代码，只报告扩展未执行。缺少当前修改阶段的必要能力时必须说明限制，不虚构执行结果。测试失败时保留失败证据并修正实现；不能执行最低验证时标记 `unverified`。

## 验收

- 默认运行时不包含安装、发布、原生验收或知识扩展正文。
- 普通代码路由只选择精简核心和当前阶段必要能力，不加载完整治理文档。
- `knowledge` 与 `maintainer` 必须显式选择，并保持现有能力可用。
- C0/R0 只读任务不启动设计、安装、发布或知识写入流程。
- C1/R1 代码任务完成完整 diff 自审和最窄相关测试；复杂或高风险任务才升级设计、计划和 Review 强度。
- 所有 profile 均通过确定性构建、清单和边界测试。

## 终审加固

终审发现 profile 过滤、安装与发布证据还需要共享同一身份边界。补充以下约束：

- 每个 profile 的 Catalog 必须包含自身条目的完整依赖闭包；构建时发现悬空依赖立即失败。
- 安装快照由版本和 artifact hash 共同寻址，profile 切换不得覆盖或激活旧 profile 的额外文件。
- 幂等安装只对相同 artifact、版本、profile、`agentsRoot`、`codexRoot` 和 `stateRoot` 成立。
- `read-only` 禁止确定性或语义自动路由，但仍允许用户显式指定只读 Skill。
- 发布证据必须记录并校验被测试 runtime 的 profile。
