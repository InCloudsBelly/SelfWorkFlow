# implement-spec 与 pr 接入审查

## 现状与本轮修订

两个技能已在仓库的文档包及显式 runtime 中接入。`implement-spec` 已有依赖图、每票独立上下文/branch/worktree、串行集成和最终单 Reviewer；普通 `implement` 上游入口没有无条件创建实现子 Agent 的指令。`pr` 有固定来源、许可、本地适配和生成方法入口，仅准备 PR 正文，不自动执行远端操作。

本轮发现的缺口是 `implement-spec` 日常选择仍要求明确的整体多票实施意图。现将选择并入已有方案决策，由主 Agent 对同一有效方案一次判断：目标与验收已清楚、至少两个可独立验收且低写冲突的工作包、预计并行或上下文隔离收益值得协调成本，才读取编排技能；小任务、高耦合、目标不清或仅步骤拆分沿常规流程。不以文件数量或 Full/Deep 触发，不另派评估 Agent、不做评分表。范围、依赖或实际能力有实质变化时重核，阶段变化本身不触发；已有领域流程分工直接复用。

技能选中后复用现有 spec/tickets；必要时在已有紧凑计划中补足最小票据与 DAG，再核验门禁并派发。无需为了选用另外调用 to-spec/to-tickets、发布 issue 或重新访谈。每票只传绑定、允许范围、验收和证据指针，不复制完整作者历史；共享文件串行，整份实施只沿既有最终审查，不逐票增加 merger 或全套 Reviewer。

普通 agent-policy 的 metadata 为 task-conditional，选择由主 Agent 完成；contract-managed Host 仍使用 explicit module ID 和真实证据，V2/V3 的 DAG、授权、能力与完成门禁保留。该变化不新增自动调度器，也不声称原 Host 能自行识别语义或新选择已在模型侧实测。

## 静态选择与反例核对

| 场景 | 预期 |
| --- | --- |
| 明确需求可自然分为两个独立验收、低写冲突的模块，存在分工收益 | 一次薄判别后读取 implement-spec，最小补齐计划/DAG与门禁，再派发 |
| 多个文件但共同修改紧耦合状态或同一文件 | 常规实施，不为凑票制造 DAG |
| 单个小修复、单票或只是若干顺序步骤 | 常规实施，不因“可列步骤”调用编排 |
| 目标/验收仍不清楚 | 沿普通范围澄清，不默认开启规格访谈与实现 Agent |
| 同一方案已判别，后续范围/依赖/实际能力有实质变化 | 重核受影响选用方式；普通阶段切换不重复判别 |
| 用户明确要求用 implement-spec 实施 | 读取并核实际前置条件，不重复做收益评估；缺门禁不派发 |
| 审查/维护 implement-spec 技能本身，或只写计划 | 不当作编排实施请求 |
| 既有领域流程已分工，例如知识更新已有主题任务 | 直接复用领域编排，不叠加通用 spec/worktree 编排 |
| 请求 PR 正文或明确创建 PR | 仅按需读取 pr，复用现有 diff/验证/风险；远端动作沿实际授权 |
| 仅审查 PR 代码、出现 PR 链接或普通任务完成 | 不自动调用 pr，不新启正文构建/验证流程 |
| 契约 Host 未选择模块或缺少 hash-bound DAG/授权证据 | 不按任务大小自动选模块，也不伪造 receipt 通过门禁 |

这些是指令与模式边界的静态核对，不是调用真实模型的任务分类测试。自动检查另外核验 frontmatter、文档/runtime 可达性、DAG 与现有路由互斥；不把本轮紧耦合维护任务拆成多个实现 Agent 试跑。
