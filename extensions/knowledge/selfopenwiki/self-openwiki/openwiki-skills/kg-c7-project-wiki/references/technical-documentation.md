# 技术文档证据与知识转换

## 先分类再吸收

- 规范/协议：区分 MUST、SHOULD、MAY，记录适用模块、版本和兼容边界。
- 设计/ADR：保留背景、约束、候选方案、最终决策、取舍和被替代状态；提案不等于已实现。
- README/接入指南：提炼入口、依赖、最小步骤和失败恢复，并用当前代码或测试验证关键命令与路径。
- 运行手册/排障记录：整理触发条件、观测信号、诊断分支、止损、恢复和验证，不复制流水账。
- 测试/性能报告：记录环境、输入、基线、指标、样本、结论与未覆盖项；“计划运行”与“实际通过”分开。
- 发布说明/变更记录：关联 commit、P4 CL、版本和影响面，只把仍成立的稳定知识合并进 canonical 页面。

## 冲突模型

同一结论冲突时按证据类型分栏，而不是静默选边：

1. `current-implementation`：当前源码、配置、生成规则和可复现测试展示的行为。
2. `normative-intent`：仍有效规范要求的目标行为。
3. `historical`：旧版本或已替代决策。
4. `contested/watchlist`：证据不足、owner 未确认或需要运行时验证。

源码优先只表示“描述当前实现”时优先；规范可能揭示实现缺陷，不能因此被删除。文档更新时间不能替代适用版本和实际证据。

## 落地方式

- 先定位现有 canonical 主题页；新文档默认增量合并，不按每份输入新建一个知识孤岛。
- 保存来源 ID/hash、标题、文档类型、适用版本、owner（若明确）和必要短摘录；其余转写为关系、约束和验证结论。
- 把“组件 A 依赖组件 B”展开为原因、接口、数据/控制流、失败模式和验证位置。
- 命令、路径、配置键和符号必须从已确认来源中取得；不能凭文档体裁补全不存在的字段。
- 对大文档先建立章节到主题页的覆盖表，避免漏掉约束，也避免整篇复制。

## 完成检查

- 文档类型、适用版本和证据状态已标明。
- 规范意图与当前实现的冲突没有被抹平。
- 关键路径、符号、配置和测试可回到来源定位。
- 临时讨论、重复背景和整份原文未进入正式 Wiki。
- 未执行验证、过期风险和待 owner 确认项被如实列出。
